  dibaca segar (`mail-messages.service.ts:228-269`); daftar memakai `accessibleMailAccountsOf` + saringan
  ulang baris (`:341-451`); folder/akun asing = 404; akun pribadi orang lain = 404 untuk Owner di daftar,

  rute `rbac-matrix.integration.test.ts` memuat 13 rute baru (3 rute token `public`) — lulus.
- **Aksi**: hak minimum per aksi (`MAIL_ACTION_MIN_LEVEL`) per pesan, `mail.send` untuk pindah/hapus
  (+ audit penolakan), `move` hanya folder akun yang sama (api `:1088` + worker `actions.ts:326`),
  `delete_permanently` hanya Kelola & hanya dari Sampah/Spam + audit jumlah; worker tidak pernah
  `EXPUNGE` biasa tanpa UIDPLUS (`imap-account.ts:759-800`), memeriksa `UIDVALIDITY` sebelum STORE/MOVE,
  pembersihan `pending_*` bersyarat `pending_action_at` (tanpa menimpa aksi baru). CHECK migrasi 0037
  (`pending_action` ↔ `pending_target_folder_id`) konsisten; perbaikan CHECK `channels_fase6_formats`
  tidak melonggarkan aturan (panjang ≤ 1.300 + pola karakter sama).
- **Token tampilan** (`mail-view-token.ts`): HMAC-SHA256/128 dengan kunci HKDF terpisah, perbandingan
  waktu-konstan, kanonik (encode ulang = token), versi, kedaluwarsa + batas masa depan; setiap pemakaian:
  sesi asal (`user_sessions` → `sessions.peek`: dicabut/kedaluwarsa/sesi 2FA-wajib ditolak), pengguna
  aktif & hak `read` dihitung ulang, pesan masih ada → selain itu 410. Token tidak berisi data pribadi,
  disensor di log api (`logger.ts:57`) dan log akses nginx dimatikan untuk `^~ /api/v1/mail/view/`
  (prefiks `^~` menang atas lokasi regex; tidak ada `add_header` yang terwarisi di lokasi itu).
- **Dokumen tampilan**: CSP `default-src 'none'` (tanpa `script-src`), `img-src` hanya origin aplikasi +
  `data:`, `font-src data:`, `base-uri`/`form-action 'none'`, `frame-ancestors` origin aplikasi,
  `sandbox allow-popups allow-popups-to-escape-sandbox` (dibuka langsung di tab pun tetap ber-origin opak
  tanpa skrip), `nosniff`, `no-referrer`, `no-store`; `X-Frame-Options` dilepas HANYA bila CSP respons
  memuat `frame-ancestors` (rute lain tetap `DENY`). CSP web `frame-src 'self'` cocok.
- **Sanitasi tampilan** (`display-html.ts`): penjaga kerumitan sebelum sanitasi; daftar izin tag/atribut;
  `on*`, `javascript:`/`vbscript:`/`data:` (juga ber-entitas/berspasi) dibuang; penanda
  `balesin-remote:`/`balesin-cid:` tidak bisa dipalsukan dari email (src non-https/cid/data dibuang) dan
  penggantian saat disajikan hanya mencocokkan `src="…"` yang dihasilkan sanitizer (teks/atribut lain
  ber-escape); `<style>` dibersihkan per potongan, `<`/`>`/`\` dibuang → tidak bisa menutup elemen; tanpa
  `url()`/`image-set()`/`@import`/`expression`/`position: fixed`. Diuji ulang dengan muatan mXSS
  (`math`/`noscript`/`svg`), `meta refresh`, `base`, `link`, `form`, `iframe` — semuanya dibuang. Walau
  sanitizer jebol, CSP + sandbox tidak menjalankan skrip dan tidak memuat apa pun dari luar.
- **Proksi gambar — SSRF**: URL hanya dari `remote_images[index]` (indeks Zod 0–199), https wajib,
  `privateCidrs: []` (privat selalu ditolak, semua alamat DNS diperiksa, sambung ke IP yang diperiksa),
  redirect ≤ 3 diperiksa ulang per lompatan, header tambahan tidak diteruskan lintas origin, tanpa
  cookie/Referer, ≤ 5 MB, jenis dari isi (raster saja; SVG/HTML → 415 GIF kosong), `nosniff` + CSP
  `sandbox`. Tanpa token `images` → 403. (Ketersediaan: lihat S5.)
- **cid**: lampiran harus milik pesan token itu, `risk ≠ blocked`, jenis raster hasil deteksi isi.
- **Lampiran**: risiko dari nama + jenis dinyatakan saat isi diambil, dipastikan dari ISI saat diunduh
  (PE/ELF/Mach-O/shebang, CFB/OLE, HTML/SVG/XML, Office bermakro → `blocked`, tidak disimpan; arsip →
  `warn` + `?confirm=1`), tidak pernah diturunkan; `Content-Type` hanya raster/PDF, lainnya
  `application/octet-stream`; `Content-Disposition: attachment` dengan nama dibersihkan (kendali/kutip/
  garis miring dibuang, bagian ASCII + `filename*`), `nosniff`, `CSP: sandbox`, `no-store`. Pratinjau
  hanya raster hasil deteksi. Sumber header: `text/plain` + `nosniff` + `CSP: sandbox`.
- **Worker isi/aksi**: sesi kerja bertenggat total 5 menit yang memutus sambungan, anggaran byte
  sambungan 96 MB + per perintah 16 MB, `fetchPart` per potongan 3 MB, nomor bagian divalidasi pola,
  payload job diperiksa ulang (akun pesan = akun payload, akun belum diputus); log hanya ID + kode.
- **WS**: event baru `mail.attachment.failed` (ID + kode) melewati saringan per akun yang sama.
- `pnpm audit`: 2 **moderate** lama, dev-only (esbuild via drizzle-kit, minimatch via eslint) — bukan
  dari perubahan ini.

## Temuan

### S5 — Tinggi — Proksi gambar luar: batas laju bukan per pengguna, tanpa batas konkurensi → OOM api & penguat lalu lintas

**Bukti**
- `apps/api/src/modules/mail/mail-messages.routes.ts:108-111`: kunci batas gambar = `token.slice(0, 32)`
  — 24 byte pertama token = versi + **ID pesan** + 7 byte ID sesi, jadi jatah 300/menit
  (`MAIL_IMAGE_RULE`, `:48`) praktis **per (pesan, sesi)**, bukan "300/menit/pengguna" (kontrak §8).
  Email lain = jatah baru; server IMAP milik CS bisa memuat ribuan email × 200 gambar.
- Batas lain hanya `MAIL_TOKEN_IP_RULE` 600/menit per **IP mentah** (`:54`, `:109` memakai
  `clientInfo(request).ip`, bukan `ipRateLimitKey` → IPv6 berganti alamat dalam /64 = jatah baru) dengan
  jendela tetap (≈ 1.200 permintaan dalam beberapa detik di batas jendela).
- `mail-messages.service.ts:662-694` → `fetchRemoteFile` (`packages/core/src/net/outgoing-webhook.ts:629-646`)
  menimbun seluruh isi (≤ 5 MB) di memori lalu `Buffer.concat` (salinan kedua), tenggat 8 dtk, **tanpa
  semaphore** per pengguna/organisasi/proses, **tanpa cache** (penyimpangan §17.4) — setiap tampil
  mengunduh ulang.
- Tes: pengguna yang sama mendapat unduhan ke-301 dalam semenit lewat token email lain (200, harusnya
  429); 30 permintaan bersamaan → 30 unduhan berjalan sekaligus (harusnya ≤ 8).

**Skenario**: CS dibobol menghubungkan akun pribadi ke server IMAP miliknya; tiap email berisi 200
`<img src="https://penyerang.tld/n.png">`. Skrip: buat token `images: "show"` untuk banyak email
(120/menit), lalu tembakkan ratusan `GET …/view/<token>/images/<i>` bersamaan. Server penyerang
meneteskan 5 MB per gambar sampai hampir 8 dtk → ratusan × 5–10 MB tertahan di proses **api** → OOM
(seluruh aplikasi, termasuk penerima webhook Meta dan WebSocket inbox); diulang setiap api hidup lagi.
Mode B (tanpa nginx depan) tidak punya `limit_req` sama sekali; Mode A `burst=200` + 30 r/s masih
≈ 400 permintaan dalam 8 dtk. Varian: URL gambar menunjuk host https pihak ketiga → server perusahaan
mengunduh ≥ 3 GB/menit per IP penyerang dari korban (penguat lalu lintas dari IP perusahaan).

**Perbaikan**
1. Batas laju gambar **per pengguna** (ambil `user.id` dari sesi asal yang sudah di-resolve; 300/menit)
   + per organisasi (mis. 3.000/menit); rute token per IP memakai `ipRateLimitKey` (/64).
2. **Semaphore** unduhan: per pengguna ≤ 4–8 berjalan, per proses ≤ 16–32; lewat → 429/503 GIF kosong
   tanpa mengunduh.
3. Kurangi memori per unduhan: tolak `Content-Length` > batas (sudah), cek 12 byte pertama (raster)
   sebelum menampung sisanya, dan pertimbangkan batas 2 MB untuk gambar email.
4. Laksanakan cache 24 jam kontrak (`sha256(url)` per organisasi, di media store dengan kuota) — juga
   menghentikan unduhan ulang & pemberitahuan ulang ke pengirim.
5. Tes: ubah dua `it.fails` S5 menjadi `it`.

### S6 — Sedang — Alamat akun pribadi (tidak terverifikasi) dihitung "domain organisasi" → peringatan penyamaran & domain mirip mati untuk seluruh organisasi

**Bukti**: `apps/worker/src/mail/read.ts:163-205` (`senderContext`) mengambil **semua** `mail_accounts`
(termasuk `kind = 'personal'`) dan **semua** `mail_identities` (termasuk `verified_at is null`) sebagai
`organizationDomains`; `mailSenderWarnings` (`packages/core/src/mail-client/content.ts:424-437`) langsung
mengembalikan `[]` bila domain pengirim termasuk daftar itu. Alamat akun tidak diikat ke kotak surat
(sisa review 9A-1 S4: CS bebas memberi label alamat apa pun pada akun pribadi ke server miliknya).

**Skenario**: CS dibobol menghubungkan akun pribadi berlabel `apa.saja@c0ntoh.co.id` (domain mirip
`contoh.co.id`). Sejak itu email penipuan `"Direktur Contoh" <direktur@c0ntoh.co.id>` ke akun BERSAMA
mana pun (`billing@`, `cs@`) tidak lagi diberi peringatan `lookalike_sender`/`impersonation` — justru
pertahanan utama terhadap penipuan transfer/invoice. Tes: kontrol tanpa akun pribadi → `lookalike_sender`;
dengan akun pribadi CS di `c0ntoh.test` → `[]`.

**Perbaikan**: `organizationDomains` hanya dari sumber yang dikelola Admin/Owner: akun **bersama**,
identitas **terverifikasi**, alamat/alias Channel Email (dan bila ada, domain di Pengaturan organisasi).
Akun pribadi & identitas tanpa `verified_at` tidak pernah memperluas "domain internal". Tes: ubah
`it.fails` S6 menjadi `it`.

### S7 — Sedang — Cache isi & lampiran tanpa kuota (disk media store bersama WhatsApp, Postgres)

**Bukti**
- `apps/worker/src/mail/read.ts:351-368` (gambar inline, ≤ 50 × 5 MB per email) dan `:552-567`
  (lampiran, ≤ 50 MB per bagian, maks. 100 bagian per email → ± 5 GB per email) disimpan ke media store
  (`MEDIA_DIR`, disk yang sama dengan media WhatsApp/Inbox) dengan `expires_at` = retensi (bawaan 90 hari,
  min. 7) **tanpa kuota** per akun/organisasi/pengguna; `mail_message_bodies` ≤ 1 MB teks + 2 MB HTML +
  64 KB header per email dibuka.
- `apps/api/src/modules/mail/mail-messages.service.ts:829-849`: setiap `GET /mail/attachments/:id`
  (240/menit/pengguna) yang belum di cache mengantre unduhan; detail (`:463-477`) mengantre isi.
- Memori worker: satu job lampiran menahan mentah ≤ ± 70 MB + string latin1 + hasil `replace` + hasil
  dekode (`content.ts:302-306`) ≈ 250 MB; `concurrency: 4` (`apps/worker/src/queues/mail.ts:508`) di
  proses worker yang juga menjalankan antrean WhatsApp/broadcast.
- Tes: akun dengan cache lampiran 20 GB tetap menyimpan lampiran baru (`status: 'ready'`).

**Skenario**: CS dibobol menyiapkan di server IMAP-nya email berisi 100 lampiran × 50 MB (nama `.pdf`,
isi acak = `ok`), lalu skrip mengunduh semuanya untuk banyak email. Worker mengisi disk berkecepatan
jaringan (puluhan–ratusan GB per jam); disk penuh → media WhatsApp gagal disimpan, Postgres (bila satu
disk) berhenti, backup membengkak; berkas bertahan sampai retensi habis.

**Perbaikan**: kuota cache per akun (mis. 2 GB) dan per organisasi (mis. 20 GB), dihitung dari
`sum(size_bytes) where storage_key is not null` (+ isi) sebelum menyimpan; lewat → pangkas LRU
(`last_opened_at`/`fetched_at`) atau tolak dengan `mail.attachment.failed { code: 'cache_full' }` + pesan
"Ruang cache email penuh; buka lewat webmail penyedia"; batas unduhan lampiran per pengguna per jam
(byte); dekode base64 per potongan (tanpa string latin1 utuh). Tes: ubah `it.fails` S7 menjadi `it`.

### R7 — Rendah — Daftar blokir nama lampiran bisa dilewati (titik di akhir, ekstensi skrip yang belum terdaftar)

`extensionOf` (`packages/core/src/mail-client/content.ts:92-94`, juga `channels/email-message.ts:471-473`)
membutuhkan `.ekstensi` tepat di akhir; `cleanFileName` (`meta/contact-identity.ts:85-93`) memangkas spasi
tetapi tidak titik → `tagihan.pdf.js.` = tanpa ekstensi → `ok` (isi teks JScript tidak terdeteksi).
Windows/Firefox membuang titik di akhir saat menyimpan → `tagihan.pdf.js` dijalankan Windows Script Host
(Chrome/Edge mengganti jadi `_`, jadi dampak bergantung peramban). `.ws`, `.vb`, `.searchconnector-ms`,
`.search-ms` (skrip WSH & konektor pencarian yang dipakai kampanye phishing) tidak ada di daftar.
Perbaikan: buang titik/spasi di akhir nama SEBELUM memeriksa ekstensi dan pada nama yang disajikan;
tambahkan ekstensi tadi (+ `msh1`, `msh2`, `mshxml`, `ps2`, `ps2xml`, `psc2`, `xbap`, `ins`, `isp`,
`mst`, `msc`); pertimbangkan pendekatan daftar-aman: ekstensi di luar daftar dokumen/media umum → `warn`
+ konfirmasi. Dikunci 2 `it.fails` (core).

### R8 — Rendah — Proksi gambar: User-Agent bermerek & tanpa cache (privasi)

`fetchRemoteFile` mengirim `User-Agent: Balesin-Media/1.0` (`outgoing-webhook.ts:593`) — kontrak §8 minta
"User-Agent umum"; pengirim pemasaran/penipu tahu perusahaan memakai Balesin (sidik produk) dan mendapat
konfirmasi baca lagi setiap email dibuka ulang (cache 24 jam ditunda, §17.4). Perbaikan: UA umum khusus
proksi email (parameter `userAgent` di `RemoteFileRequest`), cache sesuai S5 butir 4.

### R9 — Rendah — Gambar otomatis untuk pengirim "selalu tampilkan" yang belum terverifikasi

`mail-messages.service.ts:555-557`: `auto` menampilkan gambar bila pengirim ada di daftar pengguna dan
verifikasi ≠ `fail` — termasuk `unverified` (domain tanpa DMARC/SPF, atau server tanpa
`Authentication-Results` tepercaya), padahal `From` mudah dipalsukan. Penyerang memalsukan pengirim yang
sudah diizinkan → server memuat URL https pilihan penyerang otomatis saat email dibuka (pelacakan buka +
permintaan GET ke host pihak ketiga dari IP perusahaan, memperbesar S5). Perbaikan: otomatis hanya untuk
`pass`; `unverified` tetap butuh "Tampilkan gambar".

### R10 — Rendah — Satu login IMAP per email/lampiran/aksi

`createMailReader().openSession` (`apps/worker/src/mail/read.ts:104-151`) membuka sambungan + LOGIN baru
untuk SETIAP job isi/lampiran/aksi. Pengguna ber-hak Baca saja yang menyisir detail email (240/menit)
memicu puluhan LOGIN per menit ke server email perusahaan (diurutkan per akun oleh sewa kerja); banyak
server (cPHulk/fail2ban/batas login penyedia) bisa memblokir IP Balesin → sinkron semua akun di server
itu berhenti. Perbaikan: pakai ulang sesi kerja per akun selama antrean akun itu masih berisi job
(atau gabungkan job isi per akun), batas job isi per pengguna per menit (mis. 60).

### R11 — Rendah — Aksi massal tanpa rem & jejak

`act` (`mail-messages.service.ts:998-1350`): pemegang Baca & kirim bisa memindah/men-Sampah/men-Spam
100 email × 120 permintaan/menit = 12.000 email/menit dari akun bersama **tanpa audit** (audit hanya
`delete_permanently`, `:1294-1303`); pemegang Kelola non-admin bisa menghapus permanen dengan laju sama
(audit jumlah saja, tanpa pemberitahuan). Satu CS dibobol dapat mengosongkan kotak masuk bersama
(Sampah di banyak server dipangkas otomatis 30 hari). Perbaikan: audit `mail.messages.moved` (jumlah,
folder tujuan) untuk `trash`/`spam`/`move` > N email per jam; batas harian per pengguna untuk
`delete_permanently` + pemberitahuan Owner/Admin bila dilampaui (pola rem darurat SECURITY.md §5).

### R12 — Rendah — Token tampilan bisa masuk log galat nginx

`access_log off` (gateway & contoh Mode A) tidak mencakup `error_log`; galat upstream (api mati/timeout)
mencatat `request: "GET /api/v1/mail/view/<token>…"`. Token hanya 10 menit dan terikat sesi, jadi
dampaknya kecil. Perbaikan: catat di panduan operasional, atau `error_log` level `crit` di lokasi itu.

### Catatan untuk frontend (belum ada di kode yang di-commit)

Halaman peringatan `/email/tautan?ke=&tampil=` (`MAIL_LINK_WARNING_PATH`) bisa dibuka siapa pun lewat
tautan yang dirakit penyerang: hanya terima `ke` ber-skema `http:`/`https:` (tolak lainnya), tampilkan URL
lengkap + domain asli, tanpa pengalihan otomatis, tombol "Tetap buka" `target="_blank"
rel="noopener noreferrer"`. `body.text` detail email wajib dirender sebagai teks (bukan HTML).

#### P2-S8 — Sedang — Cache proksi gambar: kuota hanya menghitung baris belum kedaluwarsa, retensi 5.000 baris/hari → baris & berkas menumpuk tanpa batas

**Status: TERTUTUP (2026-11-23, agent `backend`; menunggu verifikasi `security`).**
- Retensi (`apps/worker/src/queues/mail.ts:336-365`) mengulang `delete … returning` per 5.000 baris
  sampai habis, dengan anggaran 2 menit per jalan (`:116-118`). Baris dihapus dulu, baru berkasnya.
  Jadwalnya tiap jam (`packages/core/src/queues.ts:728`).
- Kuota (`apps/api/src/modules/mail/mail-messages.service.ts:801-812`) menghitung SEMUA baris
  organisasi, termasuk yang kedaluwarsa, dengan `greatest(size_bytes, 4096)` per berkas, ditambah batas
  200.000 entri (`packages/shared/src/mail-messages.ts:48-49`). Bila penuh, gambar disajikan tanpa
  disimpan.
- Tes: `it.fails` → `it` (asersi tidak diubah), ditambah tes regresi berkas kedaluwarsa terhapus dan
  entri berlaku tetap (worker). Di api (`mail-image-proxy.integration.test.ts:224`, `:249`): baris
  kedaluwarsa ikut kuota byte, dan 200.000 entri → disajikan tanpa disimpan.

**Verifikasi `security` (2026-11-23, review 9B): TERTUTUP untuk penumpukan BARIS; SEBAGIAN untuk
BERKAS — sisanya dilanjutkan sebagai temuan 9B S5 (Sedang).**
- Retensi (`apps/worker/src/queues/mail.ts:336-365`) benar: `delete … where id in (select … limit
  5000) and expires_at <= now returning storage_key`, lalu berkas dihapus; berulang sampai batch < 5.000
  atau anggaran 2 menit; jadwal tiap jam (`packages/core/src/queues.ts:728`). Syarat `expires_at <= now`
  diulang di `DELETE`, jadi baris yang baru disegarkan `rememberImage` tidak ikut terhapus. Daya pangkas
  (≥ 100 ribu baris/jalan) > laju isi maksimum yang lolos kuota (200.000 entri/organisasi), jadi
  backlog tidak bisa tumbuh tanpa batas.
- Kuota (`apps/api/src/modules/mail/mail-messages.service.ts:804-813`) menghitung SEMUA baris
  organisasi dengan `greatest(size_bytes, 4096)` + batas 200.000 entri. Benar; lewatan karena balapan
  ≤ semafor proses (32 × 5 MB), dapat diterima.
- Tes `security-review-fase9a-2-putaran2.integration.test.ts` (worker) dan
  `mail-image-proxy.integration.test.ts` (api) dijalankan ulang: lulus. Asersi `it.fails` lama tidak
  diubah.
- **Sisa**: `rememberImage` (`:792-858`) tidak mengunci per URL dan `viewImage` (`:880-939`) tidak
  menggabungkan unduhan yang sedang berjalan. N permintaan bersamaan untuk gambar yang SAMA → N berkas
  disimpan; upsert hanya merujuk yang terakhir, dan `previous` dibaca sebelum upsert mana pun, jadi
  N − 1 berkas **yatim**: tidak dihitung kuota, tidak pernah dihapus retensi. Tes 9B: 8 permintaan
  paralel → 7 berkas, 1 baris. Dengan URL unik per putaran (`?n=…`) dan semafor 8/pengguna, laju
  berkas yatim ≈ 7/8 dari laju unduhan (≤ 300/mnt × 5 MB per pengguna). Lihat
  `docs/security-reviews/2026-11-23-fase9b.md` S5 (dikunci `it.fails` di
  `apps/api/src/modules/mail/security-review-fase9b.integration.test.ts`).

**Bukti**
- `apps/api/src/modules/mail/mail-messages.service.ts:743-765` (`rememberImage`): kuota 1 GB/organisasi
  = `sum(size_bytes)` hanya untuk `expires_at > now`. Baris kedaluwarsa yang belum dipangkas tidak
  dihitung.
- `apps/worker/src/queues/mail.ts:332-348` (`runMailCacheRetention`): satu `select … limit 5_000` untuk
  SEMUA organisasi, tanpa perulangan. Jadwalnya `MAIL_CACHE_RETENTION_INTERVAL_MS` = 24 jam
  (`packages/core/src/queues.ts:727`).
- Laju pengisian yang diizinkan: 300 entri unik/menit/pengguna (≈ 432.000/hari) dan 3.000/menit per
  organisasi. URL cukup dibuat unik per gambar, mis. `?n=1…200` di email dari server IMAP milik CS.
  Gambar 1×1 (43 byte) praktis tidak menyentuh kuota byte. Tiap entri = 1 baris + 1 berkas (≥ 1 blok
  disk + 1 inode).
- Tes: dari 6.000 baris kedaluwarsa, setelah satu jalan retensi tersisa **1.000** (harusnya 0).

**Skenario**: CS dibobol menyiapkan email berisi 200 gambar ber-URL unik dan membukanya terus-menerus
(300/mnt). Per hari ± 427.000 berkas dan baris tertinggal (± 1,7 GB blok disk + inode). Jumlahnya
terus bertambah karena pemangkasan 5.000/hari tidak pernah mengejar. Media store memakai disk yang
sama dengan media WhatsApp, jadi lama-lama inode/disk habis dan penyimpanan media WhatsApp gagal.
Pemakaian wajar (puluhan staf membuka newsletter bergambar) juga melewati 5.000 entri/hari, jadi
tumpukan terjadi bahkan tanpa penyerang. Klaim di DECISIONS bahwa berkas kedaluwarsa paling lama 48 jam
di disk tidak berlaku lagi begitu laju > 5.000/hari.

**Perbaikan**
1. Ulangi retensi cache gambar per batch sampai tidak ada baris kedaluwarsa (dengan batas waktu
   jalan), dan jalankan lebih sering (mis. tiap jam). Alternatif: hapus baris kedaluwarsa akun itu saat
   `rememberImage`.
2. Kuota menghitung SEMUA baris, termasuk yang kedaluwarsa tetapi belum dipangkas, dengan
   `greatest(size_bytes, 4096)` per berkas. Tambah batas JUMLAH entri per organisasi (mis. 100.000);
   bila lewat, gambar disajikan tanpa disimpan.
3. Tes: ubah `it.fails` di `apps/worker/src/mail/security-review-fase9a-2-putaran2.integration.test.ts`

#### P2-R14 — Rendah — Kuota ditolak tanpa penggusuran lampiran: kuota organisasi bisa dipenuhi lewat akun pribadi

Satu CS boleh punya 5 akun pribadi × 2 GB = 10 GB (setengah kuota organisasi 20 GB) dari server
miliknya. Sisanya bisa dipenuhi dengan mengunduh lampiran akun bersama yang bisa ia baca, atau dengan
mengirim email berlampiran besar ke alamat bersama. Setelah kuota penuh:
- semua unduhan lampiran di organisasi → `cache_full` sampai retensi habis (bawaan 90 hari);
- setiap isi baru menggusur 200 isi LRU dari akun MANA PUN (`read.ts:191-225`, cabang
  `organizationOver`). Ini bertentangan dengan alasan di DECISIONS ("menggusur = penyerang bisa
  mengosongkan cache orang lain").

Admin juga tidak punya tampilan pemakaian cache. Perbaikan:
- kuota gabungan akun pribadi per pemilik (mis. 2 GB total);
- saat organisasi penuh, gusur LRU berkas milik akun yang melewati porsinya (lampiran bisa diambil
  ulang dari server);
- tampilkan pemakaian cache di Pengaturan Email.

Dinilai Rendah karena butuh ≥ 5 akun bersama berisi ≥ 2 GB, atau 2 akun CS.

#### P2-R15 — Rendah — Agregasi kuota berat dijalankan sebelum rem

`GET /mail/attachments/:id` (240/mnt/pengguna) menjalankan `mailCacheUsage` SEBELUM
`serverFetchGate` (`service:1033-1049`). Kueri itu berisi 5 subkueri `sum` atas semua lampiran +
`pg_column_size` semua isi organisasi. Setiap job isi/lampiran juga menjalankannya lagi
(`read.ts:179`, `:191`). Di organisasi besar, ini beban DB yang bisa dipicu satu pengguna.
Perbaikan: panggil rem dulu, baru hitung kuota. Pertimbangkan penghitung pemakaian per akun (tabel
atau Redis) yang diperbarui saat berkas disimpan/dihapus.

#### P2-R16 — Rendah — Sisa kecil S5/R11 (dicatat, tidak wajib)

- Slot unduhan dilepas sebelum penyangga dikirim/disimpan (`service:880`, `:889`). Ini aman di balik
  nginx gateway (respons di-buffer), tetapi slot sebaiknya mencakup `rememberImage`.
- Penguat lalu lintas ke host https pihak ketiga tetap ± 300 × 5 MB/mnt/pengguna lewat URL unik; cache
  tidak membantu di sini. Ini sesuai kontrak 300/mnt; pertimbangkan anggaran byte per pengguna
  (mis. 200 MB/mnt).
- Audit pindah massal bisa dihindari dengan 9 email per permintaan (≤ 60 permintaan/jam/proses;
  penghitungnya per proses, jadi dikali jumlah replika). Pakai penghitung jumlah EMAIL per jam di Redis.
