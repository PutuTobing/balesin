## B. Temuan

### S1 — Tinggi — ReDoS di sanitasi & pemindai HTML email keluar: satu permintaan membekukan api

**Bukti**
- `packages/core/src/mail/outbound-html.ts:29` `PLACEHOLDER_ONLY = /^\{\{\s*([^{}]*?)\s*\}\}$/` dan
  `:28` `PLACEHOLDER = /\{\{\s*([^{}]*?)\s*\}\}/g`: `\s*`, `[^{}]*?`, `\s*` sama-sama bisa memakan
  spasi → backtracking **kubik** pada `{{` + spasi panjang tanpa `}}`.
- `:250-253` `hrefAllowed` menjalankan `PLACEHOLDER_ONLY` pada **setiap `href` HTML LUAR** (bukan
  hanya template) — dipanggil dari `sanitizeOutboundEmailHtml` (`:345-347`).
- `:226-228` `UNSAFE_CSS_DECLARATION = /[^;{}]*(?:url\s*\(|…)[^;{}]*;?/gi` (diulang sampai 10×,
  `:233-237`): setiap posisi awal memindai sampai `;{}` berikutnya → **kuadratik** pada isi `<style>`
  panjang tanpa `;{}`.
- `:30`/`:300` `STYLE_BLOCK = /<style\b[^>]*>([\s\S]*?)<\/style\s*>/gi` pada HTML mentah: banyak
  `<style>` tanpa penutup → kuadratik.
- Jalur API: `email-send.routes.ts:82` → `send` → `accept` → `resolveContent` (HTML ≤ 512 KB) →
  `composeEmail` → `email-render.ts:140` `renderOutboundEmail` → `sanitizeOutboundEmailHtml` (2×:
  masukan + sanitasi ulang). Hanya butuh key `email:send` dengan satu pengirim; batas laju 300/menit
  dan batas harian tidak menolong (dicek sebelum render, tetapi satu permintaan sudah cukup).
- Jalur template (Supervisor+): `email-message-templates.service.ts:885-889` (pratinjau),
  `:222`/`:230` (terbit), `:969` (kirim tes), `:1111` (`GET /public/email/templates` memindai SEMUA
  template terbit di setiap panggilan).

**Ukuran (mesin lokal, vitest)**

| Masukan | Waktu | Perkiraan |
|---|---|---|
| `<a href="{{` + 1.000 spasi + `x">` | 178 ms | |
| … 2.000 spasi | 1,3 dtk | |
| … 3.000 spasi | 4,5 dtk | 10 KB ≈ 2–3 menit; 20 KB ≈ 20+ menit (kubik) |
| `<style>` + 20 KB `a` | 0,5 dtk | |
| `<style>` + 40 KB `a` | 1,9 dtk | 512 KB ≈ 5 menit (kuadratik) |
| `'<style>'` × 20.000 (140 KB) | 0,6 dtk | 512 KB ≈ 8 dtk |
| `scanTemplateVariables`, `{{` + 2.000 spasi | 2,6 dtk | |

**Dampak.** Regex sinkron memblokir event loop proses api: selama itu **semua** permintaan berhenti —
Inbox, login, WebSocket, dan webhook masuk Meta (Meta mengulang lalu bisa menandai webhook gagal).
Penyerang dengan key n8n bocor (atau Supervisor) cukup mengirim satu permintaan < 25 KB untuk
mematikan layanan berpuluh menit, dan bisa mengulanginya. Instalasi self-hosted umumnya satu proses
api. Ketersediaan seluruh produk → Tinggi.

**Perbaikan yang disarankan**
1. Ganti pola variabel menjadi linear: `/\{\{([^{}]*)\}\}/g` dan `/^\{\{([^{}]*)\}\}$/`, lalu
   `name.trim()` di callback (tidak ada lagi kuantifier yang tumpang tindih).
2. `hrefAllowed`: tolak dulu nilai > `HREF_URL_MAX` (2.000) sebelum regex apa pun.
3. CSS `<style>`: pecah isi menjadi deklarasi dengan pemindaian karakter (`;`, `{`, `}`) lalu uji tiap
   potongan dengan regex TANPA awalan `[^;{}]*` (mis. `/url\s*\(|expression\s*\(|javascript:|…/i`),
   atau pakai parser CSS (postcss) dengan daftar izin properti yang sama seperti atribut `style`.
4. Ekstraksi `<style>`: pindai dengan `indexOf('<style')`/`indexOf('</style')` (linear) atau biarkan
   htmlparser2/sanitize-html yang mengurai elemen `style` (mis. `allowedTags` + `textFilter`).
5. Pertahanan berlapis: batasi HTML luar per elemen/atribut (mis. atribut ≤ 8 KB) dan tambahkan tes
   kinerja kasus terburuk 512 KB < 200 ms untuk semua regex di `outbound-html.ts` (juga `htmlToText`).
6. Ubah 5 tes `it.fails` S1 menjadi `it`.

### S2 — Sedang — Batas kirim email API dihitung per EMAIL, bukan per penerima; rem otomatis tidak melihat email

**Bukti**
- `apps/api/src/modules/sending-limits/sending-limits.service.ts:150-163` — batas harian key
  menjumlah `count(*)` baris `email_outbound` (1 email = 1); `:434-452` `assertCanSendEmail` tidak
  menerima jumlah penerima. Kontrak §3.2 langkah 6 sengaja "1 email = 1 berapa pun penerimanya".
- `apps/worker/src/queues/email-outbound.ts:248-262` — jendela batas per jam pengirim = `count(*)`
  baris `sent/sending/bounced`; `:382-388` dibandingkan dengan `hourlyLimit`.
- `apps/worker/src/queues/broadcast.ts:909-921` — rem otomatis (lonjakan per menit, SECURITY.md §5)
  hanya menghitung tabel `messages`; email API `conversation: "none"` (bawaan) tidak membuat baris
  `messages` sama sekali.
- Bertentangan dengan Review 9.0 S1 (Inbox: batas dihitung per penerima, `OUTBOUND_RECIPIENTS`).

**Dampak.** Satu email boleh 50 penerima (Kepada+Cc+Bcc). Dengan bawaan, key bocor bisa mengirim
500 × 50 = **25.000 penerima/hari**, dan satu pengirim 100 × 50 = **5.000 penerima/jam** (berlipat
per pengirim di daftar key), dari domain perusahaan yang lolos SPF/DKIM — tanpa alarm rem otomatis.
Akibatnya domain/IP masuk daftar hitam; tagihan asli (dan, pada mode SMTP sistem, email keamanan
seperti reset password) ikut masuk spam. Rem darurat manual & antrean ≤ 24 × batas tetap ada, jadi
bukan Tinggi.

**Perbaikan yang disarankan**
1. Batas harian key: jumlahkan `recipient_count` email + penerima pesan (`OUTBOUND_RECIPIENTS`), dan
   tolak bila `hitungan + penerima_baru > dailySendLimit`. Jumlah penerima dari body bisa dihitung
   murah (dedup tanpa beda huruf) sebelum langkah 5, jadi urutan R1 tetap.
2. Batas per jam pengirim: jendela = `sum(recipient_count)`; baris diklaim hanya bila
   `jendela + row.recipient_count <= hourlyLimit` (baris > batas sendiri: izinkan bila jendela kosong).
   Sesuaikan teks UI "email per jam" → "penerima per jam".
3. Rem otomatis: ikutkan penerima `email_outbound` (`source = 'api'`, `sending_started_at`/`sent_at`
   1 menit terakhir) ke hitungan lonjakan — atau rem khusus email dengan alarm Telegram yang sama.
4. Perbarui kontrak §3.2/§4 dan DECISIONS (#4), lalu ubah 2 tes `it.fails` S2 menjadi `it`.

### R1 — Rendah — `GET /public/email/messages/:id` membuka Bcc/metadata email milik key LAIN

`email-send.service.ts:1240-1260` memfilter `channel_id IN (pengirim key)`, bukan `api_key_id`;
`toEmailStatus` (`:448`, `:454`) mengembalikan Bcc, `metadata`, `idempotencyKey`. Key `email:read`
lain yang berbagi pengirim (mis. dasbor) melihat Bcc & metadata email billing. Batal sudah khusus key
pembuat — tidak konsisten. **Saran**: status hanya untuk key pembuat, atau sembunyikan `bcc` (ganti
`bccCount`) & `metadata` untuk key bukan pembuat. Perbarui kontrak §3.10.

### R2 — Rendah — Daftar tolak ekstensi lampiran tidak lengkap; nama berkas asli dipertahankan

`packages/core/src/mail/attachment-type.ts:16-74`: biner tak dikenal diterima sebagai
`application/octet-stream` dan teks sebagai `text/plain`, dengan **ekstensi asli tetap**. Ekstensi
pembawa malware yang belum ditolak: `.one`, `.chm`, `.msc`, `.iqy`, `.slk`, `.sct`, `.wsc`, `.scf`,
`.appx`/`.msix`, `.vhdx`, `.library-ms`, `.settingcontent-ms`, `.jnlp`, `.ps1xml`/`.psd1`, `.inf`.
Gmail menolak sebagian, tetapi webmail ISP/klien desktop tidak. **Saran**: daftar IZIN ekstensi
(pdf, png, jpg/jpeg, gif, webp, bmp, tif/tiff, csv, txt, doc/docx, xls/xlsx, ppt/pptx, odt/ods/odp),
dan ekstensi harus cocok dengan jenis hasil sniffing.

### R3 — Rendah — Unggah lampiran API tanpa kuota penyimpanan

`email-send.service.ts:1346-1406`: setiap unggahan 20 MB disimpan (kedaluwarsa = retensi media
organisasi, bawaan 30 hari) tanpa kuota; 300 permintaan/menit × 20 MB ≈ 6 GB/menit → disk VM penuh
(pola sama dengan unggahan media API WhatsApp yang sudah ada). **Saran**: kuota byte per key/hari,
kedaluwarsa unggahan API pendek (mis. 24 jam), dan alarm ruang disk.

### R4 — Rendah — Sisa data pribadi setelah hapus kontak

`contact-erasure.ts:95-114` tidak mengosongkan `idempotency_key` (sering nomor invoice/ID pelanggan),
`request_hash`, `in_reply_to`/`references` (Message-ID klien pelanggan, bisa memuat nama host/domain
pribadi). Unggahan `media_files` lewat API (berkas asli, mis. invoice PDF berisi data pelanggan)
tidak terhubung ke email sehingga tidak ikut dihapus (baru hilang saat kedaluwarsa). Pencocokan alamat
memakai bentuk huruf kecil yang disimpan; alamat kontak IDN berbentuk Unicode vs punycode di
`email_outbound` bisa terlewat. **Saran**: null-kan `idempotency_key`/`request_hash`/`in_reply_to`/
`references` (catat di kontrak bahwa kirim ulang dengan kunci lama akan membuat email baru); catat
`source_media_id` di `email_outbound_attachments` dan hapus unggahan asalnya; normalisasi alamat
kontak ke punycode sebelum pencocokan.

### R5 — Rendah — Kirim tes template mengabaikan akses per channel (9.0)

`email-message-templates.service.ts:950-963` memakai `findChannelSender` tanpa memeriksa akses
channel pengguna; Supervisor bisa mengirim tes lewat channel yang dibatasi dari dirinya. Penerima
selalu alamatnya sendiri → dampak kecil (kuota per jam pengirim, nama "Dari"). **Saran**: periksa
akses channel aktor (atau batasi ke pengirim yang bisa ia lihat).

### R6 — Rendah — QRIS: CRC hanya integritas, bukan keaslian merchant

`qris.ts:37-71` memastikan QRIS bisa dibayar, bukan milik organisasi. Key bocor bisa mengirim
"tagihan" dari domain perusahaan dengan QRIS merchant penyerang. HTML luar juga bisa memuat gambar
QR apa pun, jadi ini risiko bawaan API. **Saran** (opsional): allowlist NMID/ID merchant per
organisasi untuk isian `qris`, dan tampilkan nama merchant (tag 59) di Riwayat kirim API.

### R7 — Rendah — Sanitasi `<style>` tanpa parser CSS

`outbound-html.ts:226-241`: hanya `url(`, `expression(`, `javascript:`, `behavior:`, `-moz-binding`,
`@import`, `position: fixed` yang dibuang; `image-set("https://…")`, `@font-face`, `position:
absolute` lolos (juga `background: image-set(…)` di atribut `style`). Karena tampilan di Balesin
selalu lewat iframe sandbox + profil masuk, dampaknya hanya pemuatan sumber jarak jauh di klien email
penerima — yang toh sudah diizinkan lewat `<img src="https://…">`. **Saran**: ikut dibereskan saat
memperbaiki S1 (parser CSS + daftar izin properti di blok `<style>` juga).

### R8 — Rendah — DSN palsu dari penerima bisa menandai email "memantul" untuk semua penerima

`apps/worker/src/inbound/email-api-events.ts:56-64` (DECISIONS 9.1 #6): DSN tak baku tanpa rincian
penerima → semua penerima email ber-Message-ID cocok dianggap memantul + webhook `email.bounced`.
Message-ID diketahui setiap penerima (ada di header yang ia terima), dan `MAIL FROM:<>` mudah dipalsukan.
Penerima nakal bisa membuat n8n menandai alamat penerima lain tidak valid. **Saran**: DSN tak baku
hanya menandai penerima yang alamatnya disebut di isi laporan; atau terima DSN tak baku hanya bila
lolos DKIM dari domain MTA pelapor.

### R9 — Rendah — `fromName` bebas & berbagi reputasi dengan SMTP sistem

`fromName` boleh teks apa pun ≤ 80 tanpa `@<>` ("Bank BRI", "Tim Keamanan"); pada mode SMTP sistem
email API dikirim dari pengirim notifikasi sistem yang juga dipakai reset password/2FA
(`email-outbound.ts:471-483`), sehingga penyalahgunaan key menurunkan reputasi email keamanan.
Sesuai kontrak. **Saran**: anjurkan SMTP custom untuk channel billing di UI, dan catat `fromName`
yang berbeda dari bawaan di Riwayat kirim API.

### S3 — Tinggi (BARU) — sanitize-html super-linear pada tag bersarang dalam: api & worker beku

**Bukti (ukuran lokal)**

| Jalur | Masukan | Waktu |
|---|---|---|
| `sanitizeOutboundEmailHtml` | `<div>` × 50.000 / 100.000 | 0,36 / 1,4 dtk |
| sanitasi ulang hasil di atas (render tahap 2) | 50.000 / 100.000 (sudah ditutup `</div>`) | 3,5 / 18 dtk |
| `sanitizeEmailHtml` (profil masuk, `persist`) | 50.000 / 100.000 | 3,5 / 18 dtk |
| `renderOutboundEmail`, HTML 512 KB `<div>` | ±105.000 | **23 dtk** (ditambah ±18 dtk di `persist` bila `conversation: "create"`) |
| `POST /public/email/send`, 40.000 `<div>` (~200 KB) | | **5,3 dtk** (tes integrasi) |
| `parseInboundEmail` (worker, email MASUK) | 244 KB / 488 KB / 977 KB | 0,56 / 1,7 / 9,4 dtk |

- Penyebabnya ada di pustaka (sanitize-html/htmlparser2 memakai tumpukan tag terbuka; sanitize-html
  polos dengan `allowedTags: ['div']` juga kuadratik). Pola regex di `outbound-html.ts` tidak terlibat.
- **Jalur api** (`email-send.service.ts` → `renderOutboundEmail` 2× → `persist` → `sanitizeEmailHtml`):
  key `email:send` (atau Supervisor lewat pratinjau/terbit template) cukup mengirim HTML 512 KB untuk
  membekukan api ±25–40 dtk per permintaan. Permintaan bisa diulang beruntun (batas 300/menit), jadi
  layanan bisa mati terus-menerus.
- **Jalur worker, tanpa autentikasi** (kode Fase 6, ditemukan di review ini):
  `packages/core/src/channels/email-message.ts:548-550` menyanitasi `parsed.html` **sebelum** batas
  `EMAIL_MAX_HTML_BYTES` (512 KB) diperiksa, padahal email mentah boleh sampai 25 MB
  (`EMAIL_MAX_MESSAGE_BYTES`). Siapa pun di internet yang mengirim email ke kotak masuk channel bisa
  membekukan proses worker: 1 MB ≈ 9 dtk, beberapa MB ≈ menit–jam. Worker satu proses menjalankan
  semua antrean (`apps/worker/src/runtime.ts` `startWorkers`): kirim WhatsApp, webhook masuk/keluar,
  broadcast, email keluar. Kunci job BullMQ bisa kedaluwarsa, sehingga email yang sama berisiko
  diproses ulang.

**Perbaikan yang disarankan**
1. Sebelum sanitize-html, tolak (API: 400 `html_too_complex`; email masuk: buang HTML, pakai versi
   teks + tanda "HTML terlalu rumit") bila jumlah tag pembuka (`<` diikuti huruf) > ±20.000 atau
   kedalaman sarang > ±200. Penghitungan kedalaman cukup lewat pemindaian linear sederhana, atau
   lewat `htmlparser2` dengan penghitung `onopentag`/`onclosetag` yang berhenti di batas.
2. Email masuk: periksa `parsed.html.length` (mis. ≤ 2 × 512 KB) **sebelum** menyanitasi.
3. Pertahanan berlapis: jalankan sanitasi HTML (api & worker) di `worker_threads` dengan batas waktu
   (mis. 2 dtk → tolak/buang HTML), supaya event loop utama tidak pernah beku.
4. Ubah 3 tes `it.fails` S3 menjadi `it`. Unit dan integrasi menerima 202 **atau** 400 (dalam batas
   waktu) sebagai perbaikan yang sah. Bila perbaikan membuat `renderOutboundEmail` melempar galat,
   sesuaikan tes unit render agar memeriksa galat itu.
