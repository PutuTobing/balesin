## B. Temuan

### S1 — Sedang — Admin bisa mengalihkan semua email keamanan ke server SMTP miliknya

**Bukti.** `email-settings.routes.ts:34` (`requirePermission('settings.email.manage')`, kini Owner + Admin),
`email-settings.service.ts:454-490`. `save` hanya menulis audit `email_settings.updated` dan tidak memberi tahu
siapa pun. Semua email (undangan, atur ulang password, verifikasi, pemberitahuan 2FA/kode cadangan/akun
terkunci) dikirim worker memakai pengaturan yang tersimpan saat itu.

**Yang sudah benar (diuji):** Admin **tidak** bisa membawa password SMTP tersimpan ke host lain
(`email-settings.service.ts:211-226`). Tes koneksi dan simpan dengan host baru tanpa password dijawab 400,
dan baris tersimpan tidak berubah. Kredensial SMTP perusahaan tidak bisa dibocorkan.

**Dampak.** Dengan sesi Admin yang dibobol (cookie curian, jadi 2FA tidak lagi menghalangi), penyerang
mengganti host ke server miliknya, lalu:
1. Membaca tautan **atur ulang password CS/Teknisi**. Peran itu tidak wajib 2FA, jadi akunnya bisa diambil
   alih dan dipakai mengirim pesan ke pelanggan atas nama mereka (penyangkalan).
2. Membaca **undangan Admin buatan Owner** dan menerimanya lebih dulu. Hasilnya akun Admin kedua yang
   bertahan walaupun akun asli dinonaktifkan. Ini wewenang yang tidak dimiliki Admin (Admin tidak bisa
   mengundang Admin).
3. **Menelan pemberitahuan keamanan ke Owner** ("2FA aktif" untuk Admin baru, kode cadangan, akun
   terkunci). Deteksi yang dibangun di butir 3–4 jadi buta.

Owner tidak terancam langsung karena reset password Owner wajib kode TOTP/cadangan. Levelnya Sedang,
bukan Tinggi: butuh sesi Admin (peran wajib 2FA), dan perubahannya sendiri tercatat di audit.

**Perbaikan, sekarang:**
- Setiap `PUT /settings/email` yang mengubah `host/port/security/username/password/fromAddress` oleh
  siapa pun selain Owner memicu pemberitahuan ke **semua Owner aktif**. Isinya: siapa, kapan, IP/perangkat,
  host lama → host baru, tanpa password. Kirim lewat **pengaturan LAMA** (snapshot sebelum transaksi, kirim
  sinkron dengan batas waktu, atau job yang membawa ID versi pengaturan lama) **dan** tampilkan juga sebagai
  pemberitahuan di aplikasi untuk Owner. Penyerang tidak menguasai kanal di aplikasi. Tes
  `it.fails('Admin mengubah sambungan SMTP: Owner menerima pemberitahuan')` sudah menunggu.

**Perbaikan, fase berikutnya (sebelum produksi):**
- Konfirmasi ulang identitas (kode 2FA, mekanisme yang sama dengan "nonaktifkan 2FA") untuk perubahan
  sambungan SMTP. Ini memutus jalur "cookie Admin curian".
- Pertimbangkan masa tenggang: selama N jam setelah sambungan diubah non-Owner, email **undangan Admin**
  dan pemberitahuan keamanan untuk Owner dikirim lewat pengaturan lama (atau ditahan sampai Owner melihat
  pemberitahuannya).

### S2 — Sedang — Tidak ada izin terpisah untuk memulai percakapan ke nomor baru

**Bukti.** `permissions.ts:85-89`: `inbox.reply` = "Balas pelanggan dan kerjakan percakapan: kirim
pesan/template…", cakupan CS = `all` (`:153`). Sebaliknya, untuk API key sudah ada pemisahan
`messages:initiate` (`docs/API-N8N.md:56`, SECURITY §5 butir terakhir). Untuk pengguna tidak ada padanannya.

**Dampak.** Belum bisa dieksploitasi karena belum ada endpoint inbox. Tetapi matriks dinyatakan sebagai
sumber tunggal. Kalau Fase 2 membangun "chat baru ke nomor / kirim template ke nomor" di bawah
`inbox.reply`, akun CS yang dibobol bisa mengirim template marketing satu per satu ke ribuan nomor. Itu
broadcast terselubung yang melewati `broadcast.send` + persetujuan > ambang (SECURITY §5 "CS tidak bisa
broadcast"), menghabiskan saldo Meta, dan menurunkan rating kualitas nomor. Penahannya tinggal batas
harian dan rem darurat (Fase 4), yang datang lebih belakangan dari inbox.

**Perbaikan (ubah matriks sekarang):** tambahkan izin `inbox.initiate` (memulai percakapan / kirim
template ke nomor yang belum punya percakapan terbuka). Bawaannya Owner/Admin/Supervisor, dan CS
**opsional lewat pengaturan** jika operasional Sky Tech memerlukannya. Pertegas di komentar `inbox.reply`
bahwa izin itu hanya untuk percakapan yang sudah ada (dalam cakupan). Tambahkan juga ke tes SECURITY §5
di `permissions.test.ts`. Sebelum Fase 2 ditutup: batas harian per pengguna untuk `inbox.initiate`
berlaku sejak hari pertama, jangan menunggu Fase 4.

### R1 — Rendah — Penolakan di tingkat service tidak diaudit

**Bukti.** `invitations.service.ts:161-169`, dilempar di `:265`, `:272`, `:371`, `:431`: 403 tanpa
`recordAudit`. Hanya penolakan izin rute yang tercatat (`auth.hook.ts:116-125`).

**Dampak.** Penolakan seperti ini justru sinyal paling berharga dari Admin yang dibobol: upaya menaikkan
wewenang (mengundang Admin, mengelola undangan Admin). Saat ini tidak meninggalkan jejak. Butir 6 (ubah
peran, nonaktifkan Owner) akan menambah banyak aturan rinci sejenis.

**Perbaikan.** Sediakan `request.server.accessDenied.recordRule({ auth, rule: 'invitation.role', … })`
atau perluas `record` dengan `reason` lalu panggil sebelum `throw forbiddenRole(...)`. Pembatasnya per
pengguna × aturan. Untuk butir 6 jadikan pola wajib: setiap 403 "aturan turunan" lewat satu helper yang
otomatis mencatat audit. Tes `it.fails('Admin mencoba mengundang Admin: 403 DAN tercatat di audit')`.

### R2 — Rendah — Pencarian izin tertipu kunci prototipe

**Bukti.** `permissions.ts:168` membuat baris per peran dengan `{}`, lalu `:189`
`ROLE_PERMISSIONS[role][permission] ?? null`. `hasPermission('cs', 'toString')` → `true` (terbukti di tes).

**Dampak.** Tidak terjangkau dari luar saat ini. Izin rute divalidasi saat start (`route-access.ts:149`)
dan `permissionGrant` diketik. Tetapi web (`session.permissions` / `hasPermission`), tes, atau kode masa
depan yang meneruskan string dari JSON/parameter (mis. layar "Peran & akses" yang menerima nama izin)
akan mendapat jawaban "boleh" untuk `constructor`/`toString`. Gagalnya terbuka, padahal fungsi ini inti
keamanan.

**Perbaikan (1 baris).** `Object.create(null)` untuk baris per peran, atau di `permissionScope`:
`return Object.hasOwn(ROLE_PERMISSIONS[role], permission) ? ROLE_PERMISSIONS[role][permission]! : null;`.
Tes `it.fails('hasPermission/permissionScope: kunci prototipe …')`.

### R3 — Rendah — `settings.workspace.manage` menggabungkan rem pengiriman dengan pengaturan kerja tim

**Bukti.** `permissions.ts:49-54`: departemen, jam kerja, tag, pesan otomatis, CSAT, **dan** ambang
persetujuan broadcast, batas kirim harian, ambang alarm/biaya, dalam satu izin.

**Dampak.** Saat ini hanya Owner/Admin, jadi tidak ada eskalasi. Risikonya ada di masa depan. Permintaan
yang wajar ("Supervisor boleh mengatur jam kerja/departemen timnya") akan menyerahkan juga kendali atas
batas yang melindungi nomor (SECURITY §5). Akibatnya Supervisor bisa menaikkan ambang persetujuan lalu
mem-broadcast tanpa persetujuan.

**Perbaikan.** Pisahkan `sending.limits.manage` (ambang persetujuan, batas harian per pengguna/organisasi,
ambang rem darurat dan alarm biaya; Owner/Admin). Setiap perubahannya diaudit dan memberi tahu Owner.
Murah karena belum ada pemakai.

## C. Info (tanpa tindakan wajib)

1. **OPTIONS.** Rute modul yang menerima OPTIONS hanya terlindungi oleh plugin keamanan + CORS, bukan
   oleh hook auth atau deklarasi (`auth.hook.ts:71`, `route-access.ts:139`). Saat ini handlernya terbukti
   tidak jalan (tes baru). Usul murah: `enforceRouteDeclarations` menolak start untuk rute modul apa pun
   yang memuat `OPTIONS` (kecuali `OPTIONS *` milik CORS yang didaftarkan sebelum hook), supaya keamanannya
   tidak bergantung pada perilaku plugin pihak ketiga.
2. **Tidak mengaudit CSRF salah: setuju.** Permintaan lintas situs sudah ditolak di langkah Origin
   **sebelum** sesi dibaca (`auth.hook.ts:73-79`), jadi pelakunya memang tidak bisa dipastikan. Mencatatnya
   atas nama pemilik cookie berarti penyerang bisa mengisi audit korban. Sisa kasus (`Origin` benar, token
   salah) hampir selalu token basi. Sebagai gantinya, cukup penghitung log/metrik (`CSRF_INVALID` per
   pengguna) untuk alarm Fase 4.
3. **Audit bisa "difitnah" lewat GET lintas situs.** Cookie sesi `SameSite=Lax` (`cookies.ts:58`), jadi
   navigasi tingkat atas dari situs lain (tautan di chat) ke `GET /api/v1/settings/email` membawa cookie
   CS dan menulis `auth.access.denied` atas nama CS. Dampaknya hanya kebisingan audit. Usul: simpan
   `sec-fetch-site` (`same-origin`/`cross-site`) di metadata supaya penelaah bisa membedakannya.
4. **Volume audit.** Paling banyak 25 entri/menit/pengguna, sekitar 36 ribu/hari untuk satu akun yang
   terus mencoba. Aman untuk DB. Saat alarm dibangun, jadikan "≥ N penolakan izin berbeda dalam 10 menit"
   sebagai pemicu alarm keamanan ke Owner (pola khas akun dibobol yang memetakan endpoint).
5. **Urutan pembatas.** Penanda Redis diklaim sebelum `INSERT`. Bila `INSERT` gagal, penolakan berikutnya
   dalam 60 detik tidak tercatat (`access-denied.ts:51-71`). Dapat diterima; urutan terbalik malah membuka
   pembanjiran saat DB lambat.
6. **`permissions` di respons sesi tidak membocorkan apa pun.** Isinya hanya izin pengguna itu sendiri,
   dan matriksnya sudah ada di bundel web. Server tidak pernah memercayai daftar itu: peran dibaca dari DB
   setiap permintaan (diuji), jadi daftar basi di web hanya memengaruhi tampilan. Untuk butir 6: ubah
   peran/nonaktifkan **wajib** mencabut sesi pengguna itu (SECURITY §1, rekomendasi 11 review
   sebelumnya), supaya web juga memuat ulang izin.
7. **Petunjuk password SMTP kini terlihat Admin.** `passwordHint` = 4 karakter terakhir untuk password
   ≥ 12 karakter (`email-settings.service.ts:149`, `crypto.ts:169-174`). Entropi yang terbuka kecil. Usul:
   tampilkan "Tersimpan" saja tanpa ekor untuk sasaran kredensial pihak ketiga (juga token Meta di Fase 2).
8. **Pola cakupan untuk modul berikutnya.** `permissionGrant` + `assertWithinScope` aman untuk satu data
   (404, bukan 403). Untuk **daftar**, penyaringnya hanya ditulis di komentar (`permission-grant.ts:22-28`).
   Inilah tempat paling mungkin lupa. Usul sebelum Fase 2:
   (a) helper `scopeCondition(grant, { holder: column, linkedTicketHolder?: (userId) => SQL })` yang
   mengembalikan kondisi Drizzle, dan `switch` lengkap atas `PermissionScope` supaya nilai cakupan baru
   (departemen, Fase 5) gagal saat kompilasi;
   (b) fungsi repo daftar menerima `PermissionGrant` (bukan `organizationId` lepas) sebagai parameter
   wajib;
   (c) tes matriks kedua untuk rute bercakupan: Teknisi/CS + data milik orang lain → daftar tidak memuatnya,
   detail 404, hitungan/badge tidak ikut menghitungnya. Hitungan "Unserved/belum dibaca" sering lupa
   disaring.
9. **Teknisi "mengembalikan chat miliknya ke antrian".** Ditunda ke Fase 2 (DECISIONS). Saat dibangun,
   jangan membuka `inbox.assign` untuk Teknisi. Buat aksi khusus di bawah `inbox.reply` (cakupan
   `assigned`) yang hanya boleh "lepas ke antrian", bukan "alihkan ke X".
